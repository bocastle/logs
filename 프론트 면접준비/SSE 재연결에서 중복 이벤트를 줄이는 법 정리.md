# SSE 재연결에서 중복 이벤트를 줄이는 법 정리

## 핵심 요약

- SSE는 서버가 브라우저로 이벤트를 단방향 전송하고, 연결이 끊기면 EventSource가 자동으로 재연결하는 방식이다.
- 서버가 각 이벤트에 `id:`를 붙이면 브라우저는 재연결 요청의 `Last-Event-ID`로 마지막 처리 지점을 전달할 수 있다.
- 네트워크 경계에서는 같은 이벤트가 다시 올 수 있으므로 클라이언트 적용 로직도 멱등하게 만드는 편이 안전하다.

## 개념 설명

SSE 스트림의 `id` 필드는 브라우저가 기억하는 마지막 이벤트 식별자를 갱신한다. 재연결 시 브라우저는 이 값을 `Last-Event-ID` 헤더에 실어 보내고, 서버는 그 다음 이벤트부터 재생할 수 있다.

전송 성공과 화면 반영 사이에 연결이 끊기면 마지막 이벤트가 다시 전달될 수 있다. 이벤트 ID를 기준으로 이미 처리한 항목을 건너뛰거나 같은 상태를 다시 적용해도 결과가 같도록 설계해야 한다.

## 예시

```text
id: order-1024
retry: 3000
event: order-status
data: {"orderId":"42","status":"PAID"}

# reconnect request
Last-Event-ID: order-1024
```

서버는 `order-1024` 다음 이벤트부터 이어 보내고, 클라이언트는 이미 반영한 ID인지 한 번 더 확인한다. `retry:` 값에는 무작위 지연을 더해 동시 재연결 폭주를 줄일 수 있다.

## 면접 답변 예시

> SSE는 연결이 끊기면 `EventSource`가 자동으로 재연결합니다. 서버가 이벤트마다 유일한 `id:`를 보내면 브라우저가 마지막 값을 기억했다가 `Last-Event-ID`로 전달하고, 서버는 그 다음 지점부터 재생할 수 있습니다. 다만 전송과 화면 반영 사이의 경계에서는 같은 이벤트가 다시 올 수 있으므로 client도 이벤트 ID로 중복을 건너뛰거나 멱등하게 적용해야 합니다. 보관 범위를 지난 ID는 전체 상태를 다시 동기화하는 경로로 보냅니다.

## 장점

- 브라우저의 자동 재연결과 마지막 이벤트 ID 전달을 활용할 수 있다.
- 폴링보다 적은 요청으로 상태 변화를 전달하고 이벤트 ID 기준으로 누락 구간을 재생하기 쉽다.

## 단점

- 단방향 통신이라 client 메시지는 별도 HTTP 요청이 필요하다.
- Proxy buffering과 연결 제한이 실시간성을 해칠 수 있고, 보관 기간 밖의 ID에는 전체 동기화 경로가 필요하다.

## 주의사항 / 실무 팁

- 이벤트 ID 보관 기간과 전체 재동기화로 전환할 기준을 문서화한다.
- Heartbeat 주기와 재연결 지연에 jitter를 두고 중복 처리율, 재연결 횟수와 replay 지연을 관찰한다.
